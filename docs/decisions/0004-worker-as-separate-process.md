# 0004. Воркер как отдельный процесс

**Статус:** принято · **Дата:** 2026-10-11

## Контекст

Воркер можно запустить двумя способами:

- **внутри процесса API** — фоновый таймер в том же приложении
- **отдельным процессом** — своё приложение, свой systemd-юнит

На первый взгляд проще первый: одна команда запуска, одна единица развёртывания, никакой дополнительной настройки.

## Решение

Воркер запускается отдельным процессом. Всего на машине три процесса: `api`, `worker`, `realtime`.

## Последствия

**Хорошо:**
- **Главная причина:** тяжёлая рассылка на сотни тысяч подписчиков не отбирает время у запросов на чтение. Это вопрос доступности, а не удобства
- Падение или зависание воркера не роняет API
- Воркер можно перезапустить или остановить, не трогая API — например, чтобы разобрать зависшую рассылку
- Долгоживущие WebSocket-соединения вынесены отдельно и тоже не мешают API
- Масштабирование на PostgreSQL — просто запустить второй экземпляр `worker`, [ADR-0001](0001-sqlite-first-postgres-later.md)

**Плохо:**
- Два процесса пишут в одну базу и делят блокировку записи SQLite. Обязательны WAL и увеличенный `busy_timeout`
- Больше движущихся частей: два юнита systemd, а не один
- Нужна диагностика: «API жив, но воркер упал» — состояние, которого не было раньше

Оба минуса — это цена за доступность. Для коммерческого сервиса, где клиент шлёт уведомления о списании денег, просадка API из-за чужой массовой рассылки недопустима.

## Что обязательно при переходе

При раздельных процессах «воркер молча упал» становится реальным состоянием. Поэтому:

- `health` API проверяет не только себя, но и **свежесть** работы воркера (как давно он брал задачи)
- systemd перезапускает упавший процесс
- тревога на очередь: глубина и возраст самой старой задачи

Без этого отдельный процесс — это отдельная точка отказа, о которой никто не узнает.

## Отвергнуто

**Воркер внутри API.** Одна единица развёртывания и ноль настройки. Платит за это доступностью: тяжёлая рассылка блокирует API, и падение воркера уносит с собой всё.
