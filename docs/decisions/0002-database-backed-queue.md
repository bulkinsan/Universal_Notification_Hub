# 0002. Очередь в базе данных, а не отдельный брокер

**Статус:** принято · **Дата:** 2026-10-11

## Контекст

Нужна надёжная очередь задач: без неё рассылка выполняется внутри HTTP-запроса, отправитель ждёт минуты, а сбой посередине теряет половину уведомлений.

Стандартное решение — Redis, RabbitMQ, SQS или NATS. Все они надёжны, но это отдельный сервис: свой настройка, свой мониторинг, своя точка отказа, своё место в бэкапах.

Условия проекта: один VPS, один разработчик, коммерческий сервис.

## Решение

Очередь — обычная таблица `queue_jobs` в той же базе. Отдельного брокера нет.

Работает так:

```sql
BEGIN IMMEDIATE;
  SELECT id FROM queue_jobs
   WHERE status = 'pending' AND run_at <= :now
   ORDER BY priority DESC, id ASC
   LIMIT :batch;
  UPDATE queue_jobs
     SET status = 'processing', locked_at = :now, locked_by = :worker
   WHERE id IN (...);
COMMIT;
```

`BEGIN IMMEDIATE` берёт блокировку записи сразу при открытии транзакции, поэтому два захвата не столкнутся. При переезде на PostgreSQL та же логика выражается через `FOR UPDATE SKIP LOCKED`, и **код воркера не меняется**.

## Последствия

**Хорошо:**
- Ничего не разворачивать и не мониторить отдельно
- Очередь защищена тем же бэкапом, что и остальные данные
- По состоянию очереди видно состояние системы: одна таблица рассказывает, что происходит
- Переезд на PostgreSQL добавляет параллельных воркеров без переделки

**Плохо:**
- Очередь конкурирует с обычными запросами за ту же блокировку записи
- Высокая частота задач создаёт нагрузку на запись
- Потолок пропускной способности — один писатель SQLite

Последнее — прямое следствие [ADR-0001](0001-sqlite-first-postgres-later.md). Очередь в базе **упирается в те же ограничения**, что и остальная система, и переезжает вместе с ней.

## Когда брокер всё-таки понадобится

- Нужны несколько воркеров и очередь стала узким местом по записи
- Требования к задержке ниже, чем даёт polling раз в секунду
- Нужна маршрутизация задач между разными сервисами

До этого — лишняя деталь, которая добавит деплой, аварийный сценарий и место, где можно забыть включить подписку на события.

## Отвергнуто

**Redis + BullMQ.** Хороший выбор для Node.js. Но требует отдельного сервиса, который нужно развернуть, настроить, мониторить и не забыть в бэкапе. На одном VPS лишняя точка отказа дороже, чем выигрыш в скорости.

**RabbitMQ.** Надёжен, но избыточен: та же проблема отдельного сервиса плюс заметный порог вхождения.

**Своя реализация на файлах или сокетах.** Решается проблема «лишний сервис», но создаёт все проблемы эксплуатации разом: атомарность, восстановление после сбоя, видимость состояния, очистка. Таблица в базе даёт всё это бесплатно.
