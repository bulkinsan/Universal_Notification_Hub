# 0003. Двухстадийная раздача вместо «одна задача на уведомление»

**Статус:** принято · **Дата:** 2026-10-11

## Контекст

Первая версия очереди очевидна: вызов `POST /notify` создаёт одну задачу, а та раздаёт уведомление всем подписчикам сама.

Проблема обнаруживается на первом же реальном отправителе. Уведомление на 100 000 подписчиков — это одна задача, которая:

- выполняется часами и не помещается ни в какой разумный лимит
- при сбое повторяется целиком — то есть **отправляет всем заново**
- не даёт прогресса: по состоянию задачи непонятно, сколько доставлено
- не позволяет отменить рассылку на середине

## Решение

Разделяем работу на две стадии с промежуточным состоянием.

```
задача «раскладка» ──► создаёт строки доставки (по 500) ──►
                                                      задачи «отправка» (по 100)
                                                              │
                                                              ▼
                                                       попытка доставки
```

Строки доставки — это и есть точка отсчёта. Уведомление на 100 000 подписчиков порождает 100 000 строк, по которым виден точный прогресс.

Размер кусков ограничен намеренно: и стадия раскладки, и стадия отправки должны укладываться в разумное время. Иначе задача снова станет гигантской, только на один шаг позже.

## Последствия

**Хорошо:**
- Повтор на уровне одной доставки, а не всего уведомления
- Прогресс виден: сколько доставлено из скольких
- Уведомление можно отменить — невыполненные доставки просто пропускаются
- Можно точечно переочередить неудачные доставки
- Один медленный push-сервис тормозит свой кусок, а не всю рассылку

**Плохо:**
- Больше сущностей: задача «раскладка», задача «отправка», строка доставки
- Нужно следить за согласованностью: нельзя создать доставки, но забыть поставить задачи на отправку
- Чуть больше кода в воркере

Согласованность решается транзакцией: создание строк доставки и постановка задач на отправку происходят в одной.

## Отвергнуто

**Одна задача на уведомление.** Просто и понятно. Не выдерживает ни объёма, ни сбоев, ни отмены.

**Одна задача на каждую доставку.** Максимально мелкий granularity, повторы тривиальны. Но на 100 000 подписчиков это 100 000 строк в очереди на каждое уведомление, и polling превращается в собственное узкое место. Куски по 100 — компромисс.

**Только два этапа, без строк доставок.** Раскладка сразу шлёт и только запоминает результат. Тогда прогресс и отмена невозможны, а отправитель не может узнать, кому дошло.
