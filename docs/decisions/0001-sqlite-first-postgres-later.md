# 0001. SQLite сейчас, PostgreSQL потом

**Статус:** принято · **Дата:** 2026-10-11

## Контекст

Проект переводится из учебного состояния в коммерческий сервис с потенциально большим объёмом. Текущее хранилище — `sql.js`: WebAssembly-компиляция SQLite, которая держит **всю базу в памяти** и при каждом изменении сохраняет файл целиком. На нескольких десятках записей это незаметно, на коммерческой нагрузке это полная остановка сервиса.

При этом переход на PostgreSQL сразу — крупное вложение: другой диалект, другая модель конкурентной записи, другие инструменты, отдельный сервис на VPS. Всё это до появления первого платящего клиента.

## Решение

Начинаем с настоящего SQLite через `better-sqlite3` — нативный драйвер с настоящими транзакциями, журналом отката и режимом WAL.

Поверх — **Kysely**: типизированный построитель запросов, который для SQLite и PostgreSQL генерирует корректный SQL каждого диалекта. Это принципиально: не «писать запросы, которые случайно работают в обоих», а дать слою репозиториев знать, с какой базой он работает.

Два обязательных правила, вводимые с первого дня:

1. **SQL живёт только в слое репозиториев.** В маршрутах и сервисах его нет вообще. Смена диалекта — правка одного слоя.
2. **Дисциплина диалектов.** Запрещено то, что есть только в SQLite: автоинкремент (идентификаторы генерируем в коде), `datetime('now')` (время передаём из приложения), специфичные типы.

Второе правило важнее первого. Один запрос, написанный «по- sqlite-ски», превращает переезд из смены драйвера в переписывание.

## Последствия

**Хорошо:**
- Ноль инфраструктуры: файл базы рядом с приложением, бэкап — это копия файла
- Переезд на PostgreSQL — смена драйвера и пула соединений, не переписывание логики
- Обе базы проверяются локально, дисциплина диалектов проверяется на каждой фазе

**Плохо:**
- **Один писатель.** Второй воркер параллельно не запустить. Это ограничение SQLite, а не настройки
- API и воркер делят блокировку записи: обязательны WAL и увеличенный `busy_timeout`, транзакции должны быть короткими
- При росте нагрузки чтение упрётся в одного писателя раньше, чем запись

Оценка потолка: при 50 одновременных отправках по ~100 мс — около 250–1000 уведомлений в секунду. Для коммерческого сервиса на годы.

## Когда переходить на PostgreSQL

Триггеры, любой из которых означает «пора»:
- Нужен **второй воркер** — это главный и достаточный повод
- Растёт время ответа API из-за блокировок записи
- Появилась потребность в нескольких инстансах API
- Нужны полнотекстовый поиск или сложные аналитические запросы

Подготовка — не создавать задел, а **не создавать долги**: соблюдать правила диалектов.

## Отвергнуто

**Остаться на `sql.js`.** Само по себе неплохое решение, если строк мало. Здесь строк станет много, а библиотека упирается в память процесса и пишет весь файл на каждую запись.

**Сразу PostgreSQL.** Технически правильнее для коммерческой нагрузки, но требует инфраструктуру и экспертизу до первого клиента. Для соло-разработчика это лишний риск на старте.

**Промежуточный вариант без слоя репозиториев.** Работает на SQLite, а при переезде «починим». Не работает: правки в 40 маршрутах невозможно проверить.
