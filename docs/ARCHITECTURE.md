# Архитектура Notification Hub

Документ описывает, что это за сервис, из чего он состоит и как устроен путь уведомления от отправителя до экрана пользователя.

Прочитать его стоит до того, как менять код. Здесь объяснено простыми словами, без сокращений.

---

## 1. Что это за сервис

Notification Hub принимает уведомления от сторонних сервисов и доставляет их нужным людям.

Сервис-отправитель (банк, соцсеть, интернет-магазин) сам не умеет рассылать push своим пользователям: это дорого, нужно поддерживать инфраструктуру, Apple и Google требуют своих правил. Вместо этого он обращается к нам:

```
Отправитель  ──►  Notification Hub  ──►  Пользователь на устройстве
```

Мы берём на себя три вещи:

1. **Приём.** Отправитель отдаёт уведомление по HTTP — заголовок, текст, необязательные данные и ссылка.
2. **Рассылка.** Мы определяем, кому это уведомление нужно, и отправляем каждому тем способом, который для этого человека работает.
3. **Учёт.** Мы помним, что, кому и когда доставили. Это нужно и отправителю, и нам для разбора инцидентов.

Смысл в том, что отправителю не нужно знать ничего про устройства пользователей. Он пишет один HTTP-запрос — остальное наша забота. Это и делает сервис универсальным.

---

## 2. Основные понятия

Чтобы читать остальной документ, нужно знать семь терминов.

### Источник (source)

Сервис-отправитель. У каждого есть **домен** — уникальный идентификатор, по котору его узнают. Домен служит и брендом в интерфейсе, и ключом в базе. Пример: `bank.example.com`.

Источник может быть включён или выключен. Выключенный не виден в публичном списке и не может отправлять уведомления.

### Ключ доступа (key)

Секрет, по которому отправитель доказывает, что он — этот источник. Передаётся в заголовке `X-API-Key`.

Ключ выдаётся один раз при создании и **в базе не хранится** — только его хеш SHA-256. Поэтому если ключ утерян, его можно отозвать и выпустить новый, но посмотреть старый нельзя.

Один источник может иметь несколько действующих ключей одновременно. Это нужно для безопасной ротации: выпускаешь новый ключ, переводишь отправителя на него, и только потом отзываешь старый.

### Пользователь (user)

Человек, получающий уведомления. Опознаётся учётной записью по email или телефону.

Сейчас в коде пользователь — это случайный идентификатор в браузере, без входа. Это нужно менять: без привязки к человеку уведомления не переезжают на другой телефон, а личность держится на секретности самого идентификатора — зная его, можно прочитать чужие уведомления. Целевая модель — полноценный вход.

### Устройство (device)

Конкретный способ получать уведомления: браузер, телефон на iOS, телефон на Android. У одного человека их может быть несколько, и у каждого свой адрес доставки (push-токен или открытое WebSocket-соединение).

**Устройство и пользователь — разные вещи.** Человек один, а получать уведомления он может на трёх устройствах. В текущей схеме это не разделено, что нужно исправить.

### Подписка (subscription)

Связь «пользователь подписан на источник». Один человек может быть подписан на десяток сервисов и получать от каждого свои уведомления.

Подписка не удаляется, а помечается отменённой с датой. Это нужно, чтобы знать историю: когда человек отписался и с какого момента ему перестали слать.

### Уведомление (notification)

То, что прислал отправитель: заголовок, текст, произвольные данные, ссылка для перехода. Создаётся один раз на вызов `POST /notify`.

### Доставка (delivery)

Попытка отдать одно уведомление одному человеку одним способом. Уведомление на тысячу подписчиков порождает тысячу доставок.

Это ключевое разделение. Уведомление — это «что сказать», доставка — это «кому и получилось ли». Именно на уровне доставки ведётся учёт, повторы и разбор ошибок.

## 3. Путь уведомления

Самый важный раздел. Здесь видно, где система ломается сейчас и как будет работать.

### Как работает сейчас

```
POST /notify
     │
     ├─► проверка ключа
     ├─► запись уведомления в базу
     ├─► выборка всех подписчиков источника
     │
     └─► for каждого подписчика:            ◄── всё это внутри HTTP-запроса
              ├─► отправить push             ◄── последовательно, по одному
              ├─► записать результат
              └─► повторить
     │
     └─◄ ответ отправителю
```

Проблемы такого устройства:

- **Отправитель ждёт.** На тысячу подписчиков он получит ответ через минуты. Он может решить, что всё упало, и отправить повторно — получив дубли.
- **Всё или ничего.** Упал процесс посередине — половина подписчиков получила уведомление, половина нет, а в базе оно навсегда зависло в состоянии «в обработке». Отправитель об этом не узнает.
- **Один медленный канал тормозит всех.** Если push-сервис отвечает секунду, вся рассылка встаёт.
- **Повторов нет.** Не доставилось — значит не доставилось.

### Как будет

```
POST /notify
     │
     ├─► проверка ключа
     └─► ОДНА ТРАНЗАКЦИЯ:
          записать уведомление + положить задачу в очередь
     │
     └─◄ 202 Accepted + id            ◄── отвечает за миллисекунды
                 │
                 ▼   (позже, отдельным процессом)
          ┌──────────────┐
          │    Воркер    │
          └──────┬───────┘
                 │
     ┌───────────▼───────────┐
     │ Стадия 1: раскладка   │   подписчики → строки доставки
     │                      │   кусками по 500
     └───────────┬───────────┘
                 │  задачи «отправить» кусками по 100
     ┌───────────▼───────────┐
     │ Стадия 2: отправка    │   пробуем каналы, пишем результат
     └───────────────────────┘
```

Что это даёт:

- **Отправитель свободен сразу.** Он узнаёт, что уведомление принято, и может уйти. Результат доставки смотрит отдельно.
- **Сбой не теряет уведомления.** Незаконченные задачи после перезапуска подхватываются.
- **Повтор на уровне одной доставки.** Не доставился один push — повторяется он один, а не всё уведомление заново.
- **Параллельность.** Стадия 2 отправляет сразу много сообщений, а не по одному.
- **Виден прогресс.** По числу готовых доставок понятно, где раздача.

## 4. Как устроена очередь

### Три стадии, а не одна

Наивный вариант — «одно уведомление равно одна задача» — плох. При ста тысячах подписчиков это одна гигантская задача: она не помещается в разумное время, а при сбое повтор отправляет **всем заново**.

Поэтому работа разбита:

| Стадия | Что делает | Размер |
|---|---|---|
| **Раскладка** | Находит подписчиков, создаёт строки доставки | кусками по 500 |
| **Отправка** | Пробует отправить, пишет результат | кусками по 100 |
| **Дожим** | Догоняет то, что не отправилось сразу | по одной |

### Взятие задачи

```sql
BEGIN IMMEDIATE;
  SELECT id FROM queue_jobs
   WHERE status = 'pending' AND run_at <= :now
   ORDER BY priority DESC, id ASC
   LIMIT :batch;
  UPDATE queue_jobs
     SET status = 'processing', locked_at = :now, locked_by = :worker
   WHERE id IN (...);
COMMIT;
```

`BEGIN IMMEDIATE` — SQLite берёт блокировку записи сразу при открытии транзакции, поэтому два воркера не могут одновременно взять одну и ту же задачу. Когда дойдём до PostgreSQL, эта же логика будет выражена через `FOR UPDATE SKIP LOCKED` — **код воркера при этом не изменится**.

### Повторы

Неудачная доставка не выбрасывается, а откладывается:

```
пауза = min(30с × 2^(попытка-1), 1ч) × случайность(0.5…1.5)
```

Случайный разброс обязателен. Без него тысяча задач, упавших в одну секунду, повторятся синхронно и будут долбить push-сервис — а те блокируют за перебор.

Когда попытки исчерпаны, задача переходит в **письмо о смерти** и ждёт разбора.

### Уборка зависшего

Самая часто забываемая часть. Если воркер упал, его задачи навсегда остаются в состоянии «в работе»:

```sql
UPDATE queue_jobs SET status = 'pending', locked_by = NULL
 WHERE status = 'processing' AND locked_at < :now - :таймаут;
```

Запускается при старте воркера и раз в минуту. Длинные задачи обязаны обновлять `locked_at` по ходу, иначе их соберёт эта же уборка, пока они ещё выполняются.

### Почему доставка может повториться дважды

Если воркер упал **после** того, как push-сервис принял уведомление, но **до** отметки о выполнении — при повторе человек получит дубль. Закрыть это нельзя: протоколы push не имеют ключа дедупликации.

Мы сужаем окно (перед отправкой помечаем доставку как «в работе» и отправляем только если это удалось), но не закрываем. **Семантика системы — «хотя бы один раз».** Это нормально для push и зафиксировано как осознанный компромисс.

### Ограничение скорости

Push-сервисы (FCM, Mozilla) блокируют клиентов за перебор. Поэтому обязательны:

- не более ~50 одновременных отправок
- общий предел ~500 отправок в секунду
- учёт `Retry-After` при ответе 429
- автоматическое отключение endpoint, который систематически отказывает

### Наблюдаемость

Без этих метрик очередь — чёрный ящик:

- глубина очереди
- возраст самой старой незабранной задачи
- задач в секунду, повторов в секунду
- размер письма о смерти

Тревога поднимается при росте глубины или когда самая старая задача ждёт дольше нормы.

## 5. Устройство сервиса

Три отдельных процесса на одной машине.

| Процесс | Чем занимается | Почему отдельно |
|---|---|---|
| **api** | Принимает запросы, проверяет ключи, кладёт задачи в очередь, отдаёт статусы | Должен отвечать быстро и предсказуемо |
| **worker** | Забирает задачи, раскладывает по подписчикам, отправляет | Медленный и тяжёлый — не должен мешать API |
| **realtime** | Держит WebSocket-соединения мобильных клиентов | Долгоживущие соединения не должны мешать API |

Разделение принципиальное: зависшая рассылка на сотни тысяч подписчиков не должна отбирать время у запросов на чтение.

```
                    ┌─────────────────────────────────────────┐
   отправитель ──►  │  API-процесс                            │
   (X-API-Key)       │  принимает, валидирует, КЛАДЁТ В ОЧЕРЕДЬ │
                    │  отвечает сразу: 202 + id              │
                    └──────────────┬──────────────────────────┘
                                   │
                    ┌──────────────▼──────────────────────────┐
                    │        База данных                       │
                    │  источники · ключи · подписки ·          │
                    │  уведомления · доставки · ОЧЕРЕДЬ        │
                    └──────────────┬──────────────────────────┘
                                   │
                    ┌──────────────▼──────────────────────────┐
                    │  Воркер                                  │
                    │  забирает из очереди → раскладывает →    │
                    │  пробует каналы → пишет результат       │
                    └──────────────┬──────────────────────────┘
                                   │
 ┌────────────────────┼────────────────────┬──────────────────┐
 ▼                    ▼                    ▼                  ▼
Web Push (VAPID)  WebSocket (в сети)   APNs (iOS)        FCM (Android)
```

## 6. Каналы доставки

Канал — это способ отдать сообщение конкретному устройству. Их подключение происходит в одном месте: **реестре каналов**. Код раскладки и код отправки одинаковы для всех каналов и не знают про конкретные технологии.

Как выбирается канал:

```
Пользователь подписан на источник
        │
        ▼
Для каждого его устройства:
   │
   ├─ есть открытое WebSocket-соединение?  ──►  отправить через WebSocket
   │                                            (мгновенно, интернет есть)
   │
   ├─ нет соединения, но есть push-токен?  ──►  отправить через push-сервис
   │                                            (сработает даже на закрытом)
   │
   └─ ничего нет                            ──►  отметить «доставлено в историю»,
                                                 клиент заберёт при следующем входе
```

Последний случай важен: уведомление не пропало, оно просто подождёт, пока человек откроет приложение.

## 7. Данные

### Целевая схема

```
sources (id, name, domain, status, description, logo, created_at)
   │
   ├── source_keys (id, source_id, key_prefix, key_hash, scope,
   │                revoked_at, last_used_at)
   │
   └── notifications (id, source_id, title, body, data, status, created_at)
            │
            └── deliveries (id, notification_id, user_id, device_id,
                            channel, status, attempts, last_error, delivered_at)

users (id, email, phone, password_hash, verified_at, created_at)
   └── devices (id, user_id, platform, push_token, last_seen_at)

subscriptions (user_id, source_id, created_at, revoked_at)

queue_jobs (id, kind, payload, status, priority, attempts,
            max_attempts, run_at, locked_at, locked_by, last_error)

staff (id, email, password_hash, role, created_at)      -- сотрудники
audit_log (id, actor_id, action, target, meta, at)     -- кто что менял
```

### Чем отличается от текущей

| Сейчас | Нужно | Зачем |
|---|---|---|
| Один ключ на источник, перезаписывается | Отдельная таблица ключей | Выпустить второй, отозвать любой по отдельности |
| `users` = устройство | Пользователь и устройство разделены | Один человек — телефон, ноутбук, планшет |
| `is_active` у подписки | Дата отмены | История: когда человек отписался |
| Ключ и пароль админа в настройках | Учётные записи с ролями | В команде один человек не может всем |
| — | Журнал действий | Кто отозвал ключ, кто снял лимит |
| — | Квоты | Чтобы один отправитель не занял всю очередь |

### Путь к PostgreSQL

Схема написана так, чтобы переезд не требовал переписывания логики. Достаточно двух вещей:

1. **SQL живёт только в репозиториях.** В маршрутах и сервисах его нет. Смена диалекта — правка одного слоя.
2. **Дисциплина диалектов.** Не используем то, что есть только в SQLite: автоинкремент (идентификаторы делаем сами), `datetime('now')` (время передаём из кода), специфичные типы.

Второй пункт важнее первого. Если один запрос в одном репозитории напишут «по- sqlite-ски», переезд превратится из смены драйвера в переписывание. Дисциплина проверяется на ревью.

## 8. Чего пока нет

Честный список. Ничего из этого не сделано.

| Чего нет | Почему важно | Когда |
|---|---|---|
| Очереди и воркера | Рассылка блокирует отправителя и теряется при сбое | Фаза 2 |
| Учётных записей подписчиков | Уведомления не переезжают между устройствами | Фаза 1 |
| Ролей сотрудников и журнала действий | В команде нельзя дать доступ «на всё» | Фаза 3 |
| WebSocket и мобильных каналов | iOS и Android не подключатся | Фаза 4 |
| Админки | Некому управлять источниками и смотреть рассылки | Фаза 5 |
| PWA | Нет клиента для подписчика | Фаза 6 |
| Квот и лимитов | Один отправитель может занять всю очередь | Фаза 7 |
| Логов в файлы, бэкапов, мониторинга | Не видно проблем в проде | Фаза 8 |

Порядок фаз и их содержание — в плане работ.

## 9. Словарь

| Слово | Значение |
|---|---|
| **Источник** | Сервис-отправитель. Уникален по домену |
| **Ключ** | Секрет отправителя, доказывающий его право отправлять |
| **Подписка** | Связь «человек подписан на источник» |
| **Устройство** | Конкретный способ получения: браузер или телефон |
| **Уведомление** | То, что прислал отправитель. Одно на вызов API |
| **Доставка** | Попытка отдать уведомление одному человеку. Одна на подписчика |
| **Канал** | Способ доставки: Web Push, WebSocket, APNs, FCM |
| **Раскладка** | Стадия: подписчики превращаются в строки доставки |
| **Задача** | Единица работы в очереди |
| **Письмо о смерти** | Задача, исчерпавшая попытки, ждёт разбора |
| **VAPID** | Ключи, которыми подписываются push-уведомления в вебе |
| **Фан-аут** | Рассылка одного уведомления многим получателям |
